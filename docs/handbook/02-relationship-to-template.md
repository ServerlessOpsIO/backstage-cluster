# Relationship to the cluster template

Backstage offers an **AWS ECS Cluster** template that generates a cluster
repository much like this one. This repository was not generated by it. Its
first commit is from October 2024 and it has been maintained by hand since, so
it is laid out like a generated cluster but does not behave like one.

Read this page before copying guidance from a generated cluster's handbook, or
before pointing a template-generated service at this cluster.

## What is the same

- The repository layout: `template.yaml`, `cfn-parameters.json`,
  `cfn-tags.json`, `samconfig.toml`, and `.github/workflows/main.yml`.
- The catalog entity: a Component of type `container-cluster` with the
  `io.serverlessops/cluster-type: ecs` annotation, in the `backstage` system.
- The SSM path convention `/<Domain>/<System>/<Component>/<CodeBranch>/<name>`.
- The load balancer, HTTPS listener with a fixed default response, ACM
  certificate, and Route 53 record.
- The build and deploy workflow.

## What is different

| Area | This cluster | Cluster generated by the template |
| --- | --- | --- |
| Service discovery | No Service Connect namespace. | Service Connect default namespace `<system>.local`, published as `ServiceConnectNamespace`. |
| Capacity providers | Associates `FARGATE_SPOT` and `FARGATE`. | None declared. |
| Task execution role | One shared role, published as `EcsTaskExecutionIamRoleArn`. | None. Each service stack creates its own. |
| Task security group | One shared `ContainerSecurityGroup`, published as `ContainerSecurityGroupId`. | None. Each service stack creates its own. |
| Load balancer security group | Not published. Consumers do not need it because the shared container security group already allows it. | Published as `ClusterAlbSecurityGroupId` so each service can allow it. |
| Load balancer names | Published as `EcsAlbName` and `EcsAlbFullName`. | Not published. |
| Hosted zone ID | Plain string from the GitHub secret `ROUTE53_ZONE_ID`. | Resolved from the SSM parameter `/org/dns/ZoneId`. |
| Catalog entity | No `dependsOn` reference to a cloud-account entity. | References the selected account entity. |
| Documentation | Published by `techdocs-docs.yml`. No `mkdocs.yml`. | Ships a `mkdocs.yml`; no publishing workflow. |

## Using the ECS service templates with this cluster

The cluster appears in the service templates' **Cluster** picker, because it is
a `container-cluster` Component in the `backstage` system. A service generated
that way does not deploy against it without changes:

- The service reads `.../main/ServiceConnectNamespace`, which this cluster does
  not publish. CloudFormation fails to resolve the parameter.
- With **Use cluster load balancer?** enabled, the service also reads
  `.../main/ClusterAlbSecurityGroupId`, which this cluster does not publish.

Either publish those parameters from this cluster, or edit the generated
service to use what this cluster provides. See
[Common tasks](07-common-tasks.md#connect-an-ecs-service).

## Moving toward the template

Aligning this cluster with the template is a coordinated change, not a
drop-in replacement of `template.yaml`. `backstage-app` and `backstage-db`
depend on the shared execution role and container security group. Add what the
template publishes first, migrate the consumers, and remove the shared
resources only when nothing reads them.
