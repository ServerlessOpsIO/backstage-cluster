# Common changes and tasks

## Set up a development environment

Install the AWS SAM CLI. From the repository root, run:

```sh
sam validate --lint
sam build --parallel --template template.yaml
```

These are the checks the build job runs. Neither shows that the account's SSM
parameters, IAM permissions, or DNS are ready.

## Connect an ECS service

Deploy this cluster from `main` first. A service stack attaches by reading the
cluster's SSM parameters; `backstage-app` is the working example.

1. Declare the parameters the service needs as
   `AWS::SSM::Parameter::Value<String>` in its `template.yaml`, and set their
   values in its `cfn-parameters.json` to the names under
   `/platform/backstage/backstage-cluster/main/`:

    | Use | SSM parameter |
    | --- | --- |
    | `Cluster` on the ECS service | `EcsClusterName` |
    | `ExecutionRoleArn` on the task definition | `EcsTaskExecutionIamRoleArn` |
    | `SecurityGroups` in the service's network configuration | `ContainerSecurityGroupId` |
    | `ListenerArn` on the listener rule | `EcsAlbListenerArn` |

2. Give the service a capacity provider strategy naming `FARGATE_SPOT`,
   `FARGATE`, or both. The cluster has no default strategy.
3. Create the service's own task role for application permissions. Add an
   execution role of its own if the task definition injects secrets; the shared
   one cannot read them.
4. To receive public traffic, add a target group and a listener rule, and
   choose the rule's path and priority deliberately.
5. Add `component:backstage-cluster` to `spec.dependsOn` in the service's
   `catalog-info.yaml` so it appears under this component's dependents.

A service generated by the **AWS ECS Service Container** or **Containerized
Development Application** template expects parameters this cluster does not
publish. See
[Relationship to the cluster template](02-relationship-to-template.md#using-the-ecs-service-templates-with-this-cluster).

### Choose listener rule paths and priorities

All services share one listener at `https://platform.serverlessops.io`, and the
rules are not coordinated by any stack:

- Each priority can be used once. A second service deployed with a priority
  that is already taken fails to deploy.
- Rules are evaluated from the lowest priority number, and the first match
  wins. A `*` rule matches every request, so any rule with a higher number
  never receives traffic.
- `backstage-app` currently holds path `*` at priority `1`. A second service
  receives no traffic until `backstage-app` moves to a higher priority number
  through `AlbRulePriority` in its `cfn-parameters.json`.
- Give specific prefixes such as `/orders/*` low numbers, and reserve a high
  number for at most one catch-all service.
- The path is forwarded unchanged. A service routed at `/orders/*` receives
  requests with the `/orders` prefix.

List the rules currently on the listener before choosing, and keep a record of
assigned paths and priorities for this cluster:

```sh
aws elbv2 describe-rules --listener-arn "$(aws ssm get-parameter \
  --name /platform/backstage/backstage-cluster/main/EcsAlbListenerArn \
  --query Parameter.Value --output text)"
```

## Allow cluster tasks to reach another resource

Tasks share `ContainerSecurityGroup`, so another stack admits them by
referencing its ID, as `backstage-db` does for the database port:

1. Read `/platform/backstage/backstage-cluster/main/ContainerSecurityGroupId`
   as an `AWS::SSM::Parameter::Value<String>` parameter in the other stack.
2. Add an `AWS::EC2::SecurityGroupIngress` to that stack's own security group
   with the parameter as `SourceSecurityGroupId`.

The rule admits every task in the cluster, not one service. Give a service its
own additional security group when access must be narrower.

To let tasks call each other directly, add an ingress rule to
`ContainerSecurityGroup` in `template.yaml` whose source is the group itself.

## Change the task execution role

Edit the policy on `EcsTaskExecutionIamRole` in `template.yaml`. The change
applies to every task in the cluster, so prefer a service-specific execution
role for permissions only one service needs.

Keep the role's logical ID and leave it without a fixed name. Renaming it
replaces the role and changes the published value, and consumers hold the old
value until they redeploy.

## Change the hostname

1. Confirm the new name belongs to the hosted zone named by the
   `ROUTE53_ZONE_ID` secret.
2. Change `Hostname` in `cfn-parameters.json`, currently
   `platform.serverlessops.io`.
3. Deploy. CloudFormation issues a new certificate, switches the listener to
   it, and replaces the DNS record.

The old hostname stops resolving once the record is replaced. Every service on
the load balancer moves to the new hostname together. Update clients and any
configuration that names the old one, including the Backstage application's
own base URLs and its sign-in providers' callback URLs.

## Restrict or extend load balancer access

Edit `EcsAlbSecurityGroup` in `template.yaml` to narrow the source range, or
add resources to `template.yaml` for an HTTP listener that redirects to HTTPS,
a specific `SslPolicy`, AWS WAF, or deletion protection. Keep both security
groups in place: replacing either breaks traffic to running tasks.

The listener cannot be deleted while service rules are attached to it. Remove
each service's rule before removing the load balancer.

## Change SSM parameter paths

The parameter names in `template.yaml` are built from `Domain`, `System`,
`Component`, and `CodeBranch`; consumers write the resulting names into their
`cfn-parameters.json`. To change a path segment or a parameter name:

1. Publish the new names **in addition to** the existing ones by adding
   `AWS::SSM::Parameter` resources, and deploy the cluster.
2. Update each consumer's `cfn-parameters.json` to the new names and redeploy
   it. The known consumers are `backstage-app` and `backstage-db`.
3. Remove the old parameters from `template.yaml` once no stack reads them.

Renaming in a single step deletes the names consumers still read. Running
services continue, but none can deploy until both sides agree again.

The same steps apply to publishing the execution role's real ARN: add a new
parameter whose value is `!GetAtt EcsTaskExecutionIamRole.Arn` rather than
changing the value of `EcsTaskExecutionIamRoleArn` under its consumers.

## Add monitoring

The stack creates no alarms or dashboards and no load balancer access logs.
Add them to `template.yaml`:

- Set `ClusterSettings` on `EcsCluster` to enable Container Insights when you
  need task-level metrics.
- Add `LoadBalancerAttributes` on `EcsAlb` to deliver access logs to an S3
  bucket whose policy allows Elastic Load Balancing to write to it.
- Alarm on `HTTPCode_ELB_5XX_Count` for the load balancer. Alarms on a
  service's `UnHealthyHostCount` and `HTTPCode_Target_5XX_Count` belong in that
  service's stack, because it owns the target group.

Datadog collection is automatic; see
[Observability](06-observability.md#availability-in-datadog).

## Update this handbook

Edit the pages in `docs/handbook/` in the same change as the infrastructure
they describe. Pushing a change under `docs/` publishes it to Backstage from
whichever branch it is pushed to; see
[CI/CD pipeline](05-ci-cd.md#documentation-publishing).

## Validate and deploy changes

Run `sam validate --lint` and `sam build --parallel --template template.yaml`.
No workflow validates the template on feature branches, so these local checks
are the only validation before `main`.

Review the change for anything that replaces the cluster, execution role,
either security group, load balancer, listener, or an SSM parameter, because
each replacement affects every consumer. Commit the related template,
parameter, and handbook updates together and open a PR under your review
policy. Remember that **merging to `main` deploys**, and do not dispatch the
workflow from another ref; see
[CI/CD pipeline](05-ci-cd.md#deploying-from-other-refs).

After deployment, verify the SSM parameter values and redeploy one consumer to
confirm the contract still resolves.
