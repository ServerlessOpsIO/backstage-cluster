# Observability

## Service and task logging

The cluster stack creates no log groups and runs no containers, so it produces
no application logs of its own. `backstage-app` sends its container and sidecar
logs to CloudWatch in:

```text
/aws/ecs/<cluster-name>/<service-stack-name>
```

The cluster name is the generated value in the `EcsClusterName` SSM parameter.
A service that follows the same convention logs under the same prefix. The log
group is created on first use, which works because the shared task execution
role allows `logs:CreateLogGroup`. Groups created this way have no retention
setting unless the service or the account applies one. Investigate application
behavior in the consuming service's handbook and logs.

Cluster changes themselves are recorded in the CloudFormation stack events and
the GitHub Actions deployment logs.

## Load balancer logging

The template does not enable load balancer access logs or connection logs, so
there is no per-request record at the shared entry point: not the client
address, the matched rule, or the target that answered. Requests are visible
only as metrics, and in the logs of the service that received them.

Enable access logs to an S3 bucket through `LoadBalancerAttributes` on `EcsAlb`
if you need request-level investigation or an audit trail; see
[Common tasks](07-common-tasks.md#add-monitoring).

## Metrics

ECS publishes `CPUUtilization` and `MemoryUtilization` for each service in the
cluster. The template does not set `ClusterSettings`, so CloudWatch Container
Insights follows the account's default setting. Container Insights adds
task-level and container-level metrics at additional cost.

The load balancer publishes standard `AWS/ApplicationELB` metrics, including
`RequestCount`, `TargetResponseTime`, `HTTPCode_ELB_4XX_Count`,
`HTTPCode_ELB_5XX_Count`, `HTTPCode_Target_5XX_Count`, and, per target group,
`HealthyHostCount` and `UnHealthyHostCount`. The `LoadBalancer` dimension of
these metrics is the value in the `EcsAlbFullName` SSM parameter.

Read them with the routing model in mind:

- Target-group metrics exist only once a service attaches a target group, and
  belong to that service.
- Requests answered by the default fixed response count toward `RequestCount`
  and `HTTP_Fixed_Response_Count` without reaching any service. While
  `backstage-app` holds a `*` rule, no request takes this path.
- `HTTPCode_ELB_5XX_Count` counts errors generated by the load balancer itself,
  such as a rule whose target group has no registered task.
  `HTTPCode_Target_5XX_Count` counts errors returned by a service.

Services that use `FARGATE_SPOT` can have tasks interrupted by AWS. An
interruption appears as a stopped task with a Spot interruption reason in the
service's events, not as a cluster or deployment failure.

The template does not configure alarms or dashboards. Add these intentionally
based on the reliability targets of the services that share this cluster.

## Availability in Datadog

The Datadog AWS integration and log shipping are **configured automatically in
all AWS accounts**. Developers do not need to enable the integration or
configure log forwarding. Use Datadog to inspect the cluster's AWS metrics, the
load balancer's metrics, and the shipped logs of the services that run in it.

Baseline tagging is also automatic: `cfn-tags.json` supplies `org:domain`,
`org:system`, and `org:component`, and `ServerlessOpsIO/gha-deploy-aws-sam` adds
additional deployment tags. This stack's `org:domain` tag is `infra`, not
`platform`; filter accordingly. See
[Configuration](03-configuration.md#stack-tags-cfn-tagsjson).

Services can also run a Datadog agent sidecar, as `backstage-app` does. That is
separate from the account-level integration described here and is not
configured by this cluster.

In Datadog Metrics Explorer, filter the imported AWS metrics by the cluster
name or load balancer, or by the `org:*` tags. Exact field names and tags
depend on the integration's configuration. If data is missing, first confirm it
exists in CloudWatch and check the Datadog time range and resource/tag filters.
Treat persistent missing data as a problem with the existing collection or
shipping configuration, not a requirement to set up a new integration.

## Investigation checklist

Most cluster problems surface as a service that will not deploy or cannot be
reached.

1. Note the timestamp, the affected service, the workflow run and ref, and the
   target account and region.
2. For a failed cluster deployment, read the build/deploy logs and the
   CloudFormation stack events for validation, permission, or
   resource-creation failures.
3. For a consumer that fails to deploy with a missing parameter, compare the
   SSM names in its `cfn-parameters.json` with the parameters listed in
   [Features](01-features.md#ssm-integration-contract). Check the account and
   region, and that the cluster was last deployed from `main`.
4. For a task that fails to start, read the stopped-task reason. Image pull and
   log group errors point to the shared execution role; a failure to fetch a
   secret means the task needs permissions this role does not grant.
5. For a request that returns `{ "healthy": true }`, no listener rule matched:
   check the service's path pattern and that its rule exists on the listener.
6. For a `502` or `503`, a rule matched but its target group could not serve
   the request: check target health and the service's health check, then the
   service's events, stopped-task reasons, and container logs.
7. For a request that reaches the wrong service, compare rule priorities; a
   broader path pattern with a lower priority number wins.
8. For a service that cannot reach the database, check that its tasks use the
   shared container security group and that `backstage-db` still references
   the current group ID.
9. For TLS or name-resolution failures, check the certificate's status and the
   Route 53 alias record.
10. Check Datadog ingestion separately if CloudWatch data is present but
    missing from Datadog.

Do not copy secrets or sensitive request data into tickets.
